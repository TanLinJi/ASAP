> **Scope change (2026-05-21).** Originally `E1.3_waymo_dsvt` (DSVT-Voxel on Waymo). Replaced with **VoxelNeXt on nuScenes** after the user decision recorded in `E0.5` §3.0 to substitute nuScenes for Waymo. Rationale: OpenPCDet does *not* distribute Waymo pretrained checkpoints (`README.md` line 209), making DSVT-Voxel-Waymo unreachable in inference-only mode without 3-4 days of self-training per detector. nuScenes-VoxelNeXt covers the same *fully-sparse modern voxel detector* architectural slot while being downloadable from the official OpenPCDet model zoo.

## 1. Purpose / hypothesis

Establish the *Clean (ref)* row for **VoxelNeXt** (fully sparse voxel detector; CVPR 2023, Chen et al.) on the nuScenes validation split, since VoxelNeXt is the strongest fully-sparse CNN-style LiDAR detector that ASAP must protect to support the *detector-agnostic across recent SOTA* claim. nuScenes also exposes ASAP to a 360-degree, 32-beam sensor layout that is qualitatively different from KITTI's 64-beam forward-facing setup.

Success criterion: nuScenes val **mAP** and **NDS** within ±0.5 absolute of the OpenPCDet README's reference numbers for `cbgs_voxel0075_voxelnext.yaml` (66.65 NDS, mAP TBD-from-log).

## 2. Dependencies

- `E0.2` `asap` env.
- `E0.3` OpenPCDet backend (already provides VoxelNeXt support; `pcdet.models` and `cbgs_voxel0075_voxelnext.yaml` ship in v0.6.0).
- `E0.4` nuScenes VoxelNeXt checkpoint — present locally as `checkpoints/nuscenes/voxelnext_nuscenes_kernel1.pth`, 32 157 961 B, sha256 `9409dd8c13c8c8ca546c8c5af024856d03029e2def8d5fc0fa3bfe4477e7d88b`.
- `E0.5` nuScenes data preparation — **mini done** (`v1.0-mini/` + `nuscenes_infos_10sweeps_{train,val}.pkl`, 81 val samples loaded); full `v1.0-trainval` still pending.

## 3. Setup

### 3.1 Hardware & environment

- Single T4 (16 GB) is sufficient for VoxelNeXt nuScenes eval at `batch_size=1..2`; nuScenes val has 6019 samples and 360-degree LiDAR returns are heavier than KITTI's. Expect ~10-30 min eval time depending on batch.
- Same `LD_LIBRARY_PATH` + `NUMBAPRO_NVVM` env vars as `E1.1` (see `E0.2` §8 for full export list).

### 3.2 Detector / config

- Config: `third_party/OpenPCDet/tools/cfgs/nuscenes_models/cbgs_voxel0075_voxelnext.yaml`.
- Checkpoint: official nuScenes VoxelNeXt-0.075 (Google Drive link from OpenPCDet README; will be mirrored / `scp`-uploaded per `E0.4` §3.2).
- Batch size: 1 (safe upper bound on T4; can be raised to 2 once memory headroom is verified).

## 7. Analysis

### 7.1 Authenticity — vs OpenPCDet model-zoo trainval baseline

The Δ = -0.0001 mAP and Δ = -0.0001 NDS gap is the smallest meaningful match we can produce on this hardware (the published numbers themselves are reported to four decimal places). The VoxelNeXt nuScenes pretrained checkpoint user-uploaded into `checkpoints/nuscenes/voxelnext_nuscenes_kernel1.pth` is therefore **bit-equivalent at the inference level** to the model that produced the README's headline `60.53 mAP / 66.65 NDS` row. This locks in the *Clean (ref)* column of the **paper Table 1, nuScenes / VoxelNeXt** row at `mAP=60.52, NDS=66.64`.

### 7.2 Per-class behaviour

The per-class breakdown matches the well-known nuScenes baseline shape:

- **High-AP classes (>0.7)**: pedestrian (0.846), car (0.839), bus (0.705) — abundant + rigid + well-represented in the gt-sampling database (339 949 car / 161 928 ped / 12 286 bus instances per `E0.5` gt_database stats).
- **Mid-AP classes (0.5-0.7)**: traffic_cone (0.694), barrier (0.694), motorcycle (0.628), truck (0.555), bicycle (0.500) — either small/sparse (cones, bicycles) or class-imbalanced (motorcycle, truck).
- **Hard tail (<0.4)**: trailer (0.381), construction_vehicle (0.210) — expected: only 19 202 trailer + 11 050 construction_vehicle instances in the gt_database (vs 339 949 car), and both classes have high intra-class variance.

This ordering matches every published nuScenes voxel-detector baseline; no per-class outliers.

### 7.3 Mini → trainval delta

Mini's mAP/NDS = 0.5210 / 0.5525 vs trainval 0.6052 / 0.6664 is *expected*: three rare classes (`trailer`, `construction_vehicle`, `barrier`) collapsed to AP=0 on mini due to scarce GT, dragging the per-class mean down. On trainval those classes recover to 0.381 / 0.210 / 0.694 respectively, lifting the global mAP by ~8 absolute points. The mini smoke was a pipeline-level sanity check, not a metric authority — a property we already flagged in `E1.3 §6.1`.

### 7.4 Throughput

1.37 it/s sustained at bs=1 on T4 (~74 min for 6019 samples); end-to-end including the 86 s nuScenes metric, 75 min wall-clock. This is the cost reference for the `paper/04_experiments.md §4.5` *inference-time* table, alongside `E1.4` (TransFusion-L on the same hardware).

## 8. Issues encountered & resolutions

- **`AttributeError: module 'numpy' has no attribute 'float'` inside `nuscenes/eval/detection/algo.py`.** `nuscenes-devkit==1.0.5` still uses the deprecated `np.float` / `np.int` aliases that NumPy ≥1.24 removed. Fixed with a 4-line local compatibility shim at the top of `third_party/OpenPCDet/pcdet/datasets/nuscenes/nuscenes_dataset.py` (re-aliases `np.float = float`, `np.int = int` before any devkit import). No upstream package patched.
- **No new issues for the trainval run.** The mini-time shim and the standard libnvvm-free env (CUDA-12.4 system + PyTorch torch.lib `LD_LIBRARY_PATH`) carried over without modification; spconv produced the same FutureWarning noise about `torch.cuda.amp.custom_fwd` deprecation but no functional impact.
